# Internacionalizacion

La web usa `next-intl` con locale seleccionado en la cookie `NEXT_LOCALE` y sin prefijo de
locale en las URLs (configuracion `localePrefix: "never"` en `src/i18n/routing.ts`).
El espanol (`es`) es el locale por defecto; los catalogos son `messages/es.json` y
`messages/en.json`.

## Agregar un idioma nuevo

1. Crea `messages/<locale>.json` con las mismas claves (por feature) y los mismos
   placeholders de interpolacion que `messages/es.json`.
2. Agrega el codigo del locale a `locales` en `src/i18n/routing.ts` y, si aplica, el `timeZone`
   correspondiente en `src/i18n/request.ts`.
3. Revisa la lista de locales soportados en la API (validacion de `AppUser.Locale`) y agrega el
   codigo nuevo si se habilita para usuarios autenticados.
4. Un test (`src/i18n/messages.test.ts`) exige que todos los catalogos tengan exactamente las
   mismas claves; ejecuta `pnpm test` para verificarlo.

## Reglas

- Todo texto de UI va en `messages/es.json` y `messages/en.json`; nunca hardcodeado.
- La API no traduce: devuelve un `code` y la web lo traduce con `errors.<code>`.
  Todo codigo de error nuevo requiere traduccion en ambos idiomas.
- Los nombres de modulo y sus traducciones llegan desde `/auth/me` (traducciones del propio
  `IModuleDefinition` en la API).
- El locale del usuario autenticado se guarda con `PUT /api/auth/me/preferences` y se propaga
  a la cookie `NEXT_LOCALE`.
